Decision Change Lab

Status: documentation blueprint. Implementation has not started. This repository contains a proposed product, architecture, build sequence, evaluation protocol, and original synthetic example. There is no runnable application, completed benchmark, or demonstrated performance yet. All acceptance targets below are unachieved.

Decision Change Lab asks: when facts change after approval, which pending decisions should be checked again, and which completed decisions need investigation? The first workflow is a simulated purchase-order amendment. It links decisions to source versions, replays changes, and compares four revalidation strategies under the same final execution check.

Reports identify the operational problem; this exact product is our hypothesis. PwC’s governance discussion motivates accountable ongoing oversight. McKinsey’s procurement analysis supplies a relevant business workflow. Neither establishes demand, novelty, or the effectiveness of this design. Sources and rationale separates evidence from inference.

Start here

  1. Read requirements to understand the user, boundaries, and numbered requirements.
  2. Read architecture before implementing the state model, clock, or dispatch control.
  3. Work through the build plan in dependency order; maintain the tracker.
  4. Freeze the evaluation protocol before opening the held-out cases.
  5. Use definition of done as the release gate, then publication runbook.
  6. Keep delivery decisions and risks current using actual evidence.

What is here now

  • Eight design and delivery documents.
  • An original synthetic supplier-hold scenario, its schema, and specified expected outcome.
  • Example-reading instructions and an expected-result schema.
  • An implementation tracker, ignore rules, and optional model configuration example.

The expected outcome is a specification, not output from a working system. No private operational data is needed. The example is separate from the planned development and held-out datasets.

Intended release

Proposed stack: Python 3.12, uv, SQLite, a command-line runner, and a read-only local report. FastAPI is an optional local interface after the core works. The deterministic demo must run without a model provider or API key. An optional model adapter proposes amendments and dependency candidates; it cannot execute actions.

Version 1 should ship a reproducible demo, four baseline implementations, tests for consequential state transitions, 2,400 deterministic control episodes, and a separately reported agent-input study with 120 cached proposal-generation samples replayed across four strategies for 480 episodes if its budget and implementation gates pass. An incomplete agent evaluation must be prominently marked incomplete; it cannot be counted as delivered.

No install command is available today. Commands in the build plan are explicitly FUTURE interface contracts, to implement and verify before copying them into a runnable quick start.

Scope and limitations

This is a local simulator for research and operational-control design. It does not place real orders, transfer money, reverse completed transactions, certify compliance, or prove losses prevented. Atomicity claims apply only to the specified SQLite transaction boundary. Unknown source changes, incomplete dependencies, and delayed human review remain visible limitations.

A useful negative result is acceptable. A selective strategy must earn any efficiency claim against the same guard and evidence used by its baselines; blocking all decisions is not success.

01 — Product requirements

Status: proposed requirements, not implemented. Read architecture next.

Problem, user, and end state

A procurement operations reviewer approves an amendment using the information available at that moment. Later, a supplier is suspended, a price is corrected, or approval authority changes. A historical approval can remain authentic while its justification becomes stale. A generic event log does not by itself determine which decisions need attention.

The primary user is the reviewer responsible for purchase-order amendments. An automation owner configures rules and investigates failures. A researcher needs reproducible comparisons. These are proposed users; interviews and adoption have not been established.

The end state is a local demonstration where one changed supplier affects a pending amendment and a previously committed, still-open order, while an unrelated amendment can proceed. A reviewer sees the change, supporting records, applicable rule, affected decisions, and available next step. The same histories can be replayed through four strategies and scored without exposing the answer key to those strategies.

User stories

ID Story Observable acceptance
US-01 As a reviewer, I need to know which facts an approval relied on. Every approved revision has record IDs, source versions, policy version, and an approval binding.
US-02 As a reviewer, I need relevant changes separated from unrelated changes. A supplier-A hold targets dependent decisions; supplier-B decisions remain eligible if their own checks pass.
US-03 As an automation owner, I need a stale amendment stopped at dispatch. The shared final guard rejects a known-invalid amendment inside the local transaction.
US-04 As a reviewer, I need completed work investigated without silent reversal. A committed order keeps its committed status and receives an investigation case.
US-05 As a researcher, I need fair comparisons and observable failures. Identical scenario/schedule inputs reach each strategy, and all failed or timed-out runs remain in the report.

Functional requirements

Proposed business rules for version 1

Use one simulated currency, USD, represented as integer cents, and integer units. An amendment contains an order ID, supplier ID, quantity, unit price, and requested delivery date. It must satisfy all of the following at dispatch: supplier active; positive bounded quantity; unit price and total within the current contract/policy limits; current authorized approval for the exact revision; and an open order eligible for amendment. Derive totals deterministically, never from model arithmetic.

A changed value does not necessarily require escalation. Revalidation can establish that a change was benign; it records work but leaves a valid approval usable under the frozen policy. If the decision remains substantively valid but its bound source versions change, issue a new machine revalidation proof referencing the original human approval and current versions. This is allowed only when the frozen policy explicitly permits it; a substantive amendment or authority change requires a new human approval. Never silently rebind an approval across a material change.

For this benchmark, an open committed order linked to a newly suspended supplier requires an investigation, even if it was valid when committed. This is a synthetic workflow rule, not an assertion about procurement law or universal practice. A completed investigation records a reviewer disposition; it does not undo the original order.

Nonfunctional requirements and non-goals

  • Reproducibility: pin dependencies and runtime, record the code revision and configuration, and separate virtual time from measured runtime.
  • Inspectability: explain a hold with a rule and source references, rather than a model’s unsupported narrative.
  • Bounded execution: configurable per-run step, duration, and optional model-spend limits; distinguish error from a business rejection.
  • Recovery: a crashed transaction leaves no partial execution. Database rebuild from fixture plus durable audit input is testable.
  • Local isolation: no live credentials, remote execution endpoint, public upload, multi-tenant authorization, distributed transaction, real payment, or production ERP connector in v1.
  • Research integrity: no promise that selective revalidation wins, that synthetic cases represent all incidents, or that the design is novel.

An optional UI visualizes existing state. It must not become a prerequisite for evaluating the system. Production authentication, high availability, distributed event delivery, and customer-data integration require a separate scope and threat model.

02 — Proposed architecture and contracts

Every choice here is proposed. There is no implementation yet. Architecture changes require a decision-log entry and corresponding protocol review.

Components and ownership

scenario -> validator -> clock/replay -> versioned facts + event log
                                        |                 |
                                        v                 v
                                  policy evaluator <- strategy selector
                                        |                 |
                         approval/revalidation proof -> case queue
                                        |
                                common dispatch guard
                                        |
                             simulated order mutation

hidden truth + output traces -> isolated evaluator -> aggregate report
optional agent -> validated proposal/dependency candidates -> normal review path

Use Python 3.12 and a uv-managed package. The core uses SQLite and standard-library arithmetic/time primitives; propose Pydantic for typed boundaries, jsonschema for fixture validation, pytest for tests, and Ruff for linting. Pin exact versions during WP-02 instead of treating a version guess as tested compatibility. The CLI is the primary interface. A later local FastAPI adapter calls the same application services; it must not implement a second dispatch path.

Suggested implementation layout is src/decision_change_lab/ with domain/, storage/, policies/, strategies/, replay/, agents/, evaluation/, reports/, and cli.py. Keep hidden labels outside the package runtime input. A shared fixture/event utility may later be extracted into a versioned package, but this repository must install independently and must not import sibling repositories by relative path.

Data model

Table or object Identity and important fields Invariant
source_events event_id; source_id + source_event_id; entity kind/ID; source_version; effective_at; observed_at; canonical payload/hash Unique delivery identity; conflicting reuse is rejected, not overwritten.
fact_versions entity kind/ID + source_version; effective interval; observed time; payload; correction reference History remains queryable; ingest order does not determine business-effective order.
decision_revisions decision_id + revision; proposed payload/hash; created_at; status; open_obligation A changed payload creates a new revision.
decision_dependencies revision; entity kind/ID; field path; recorded version; origin Separate supplied, extracted, and injected-missing-edge conditions.
approvals approval_id; revision/hash; actor; policy version; source digest; granted/expiry/revoked times No approval can authorize a different revision or payload.
revalidation_proofs proof_id; approval_id; checked knowledge time; versions; rule outcomes Fresh proof never silently expands the original authority.
dispatch_receipts idempotency key; request hash; result; execution ID; checked versions; committed_at At most one simulated mutation for one request.
investigations case_id; decision_id; triggering change; reason; owner; status/disposition Unique case for the same decision/change/reason.
audit_events monotonically assigned sequence; virtual timestamp; actor; object ID; reason; source references Causal order can be reconstructed without assuming timestamps are unique.
runs run ID; dataset/config/code digests; strategy; schedule; seed; status; counters An error run is retained and cannot silently disappear.

Use SQLite foreign keys, explicit uniqueness constraints, and schema migrations with a recorded version. Do not serialize floating-point money. Canonical payload hashing uses UTF-8 JSON with sorted keys, consistent separators, and no NaN; document this encoding and test it across processes. A hash establishes record equality, not truth or legal authenticity.

Time and knowledge

Accept timezone-aware RFC 3339 timestamps; normalize to UTC and integer microseconds internally. Reject naive dates/times at event boundaries. Persist the original timestamp string when useful for debugging. The virtual clock advances from the schedule; real monotonic time measures performance only.

effective_at says when the source claims the fact became applicable. observed_at says when this simulator received it. A query at knowledge time K may use only versions with observed_at <= K. For business time T, select the applicable effective interval among those versions according to explicit source version/correction rules. Never use a future observation merely because its effective date is earlier.

Proposed precedence: a correction explicitly supersedes its referenced version for the stated interval; otherwise choose the greatest effective start not after T, then the greatest source version for a tie. Reject ambiguous overlapping intervals without a defined supersession. Backdated corrections remain new observations. Future-effective changes are stored and activate at their effective time after they are observed. Cross-source conflicts produce a review condition, not an arbitrary last-write winner.

State transitions

Pending revision: proposed -> approved -> committed, with approved -> on_hold, on_hold -> proposed by creating a revised proposal, and explicit cancellation before commit. A new approval can restore an unchanged held revision only after all required checks pass. An expiry creates a freshness review, not automatic rejection of a business-valid action.

Committed orders stay committed. Their independent case state is none -> open -> assigned -> resolved. Resolution requires a disposition such as confirmed acceptable, contact supplier, or manual remediation required. Automatic reversal is out of scope. Repeated events cannot create repeated cases for the same cause.

The policy evaluator is a pure function of a proposed amendment, permitted facts, policy, and current authority. It returns valid, invalid, or insufficient_evidence, reason codes, and supporting record IDs. Strategy selectors decide which decisions to evaluate and when; they do not change business truth or available actions.

Shared final dispatch boundary

All four strategies call the same service. The guard derives required supplier, order, policy, contract, and approval records from the typed amendment and fixed policy rules, rather than trusting the selective strategy’s possibly incomplete dependency graph. It sees only currently observed facts. This means missing dependency capture can harm early detection while the guard still prevents a known-invalid pending execution. That is the intended fair comparison.

Proposed local transaction procedure:

  1. Validate the request and canonical request hash. Do model calls and expensive preparation outside the transaction.
  2. Open BEGIN IMMEDIATE with an explicit, bounded busy timeout and retry policy. The writer lock covers source materialization and simulated execution in this same database.
  3. Check the idempotency receipt. Return the prior result for the same key/hash; reject a changed request using that key.
  4. Re-read decision revision, latest visible source versions, approval/revocation state, current policy, and order status inside the transaction. Ignore earlier preflight success.
  5. Evaluate the fixed dispatch rules. On a business rejection, persist the receipt, reason, and hold atomically; do not mutate the order.
  6. On success, conditionally update the order using its expected version, create the execution receipt, and append the audit event. A zero-row conditional update is a conflict and must not count as execution.
  7. Commit once. On exception, roll back and return an infrastructure error. Never report success before commit.

A source writer scheduled between preflight and the transaction must become visible to step 4. A competing writer after the transaction starts must wait or fail; it cannot alter the checked state before this local commit. A change learned after commit can create an investigation but cannot retroactively make the earlier knowledge available. Test both orders with independent SQLite connections and deterministic barriers. Do not claim this boundary spans an external ERP API. SQLite’s transaction documentation describes the single-writer behavior used by this proposal.

Proposed service/API contracts

The CLI calls these services directly. HTTP paths below are optional future adapters, not implemented endpoints. For every mutation use a request ID; execution additionally requires an Idempotency-Key. Errors return {code, message, request_id, details} with stable codes and no secret values.

Service / optional path Required input Successful output Rejection cases
ingest / POST /v1/events Event envelope and payload event_id, accepted/duplicate, observed_at 422 invalid; 409 identity conflict
propose / POST /v1/decisions Amendment, dependency candidates, origin decision_id, revision, proposed status 422 bad references or amounts
approve / POST /v1/decisions/{id}/approvals revision, payload hash, actor, expiry approval_id and bound source digest 409 stale revision; 422 unauthorized actor in fixture
review / POST /v1/decisions/{id}/revalidate revision, cause event, knowledge time outcome, reasons, proof/case IDs 409 conflicting revision
dispatch / POST /v1/decisions/{id}/dispatch revision, approval_id, expected order version, idempotency key receipt with committed execution or replayed receipt 409 stale/conflict/invalid; 503 busy/error
case / GET /v1/investigations/{id} case ID change, evidence references, status, owner 404 unknown case
disposition / POST /v1/investigations/{id}/disposition expected case version, actor, disposition new case version and audit entry 409 concurrent change
replay / CLI dcl replay fixture, strategy, schedule, seed, output manifest + traces + summary Nonzero exit for infrastructure/validation failure

A rejection receipt also binds its key: retrying the exact request returns that rejection. A new approval or changed amendment requires a new request/key. Runtime request IDs and keys are supplied by the caller or generated once by the CLI, never regenerated during retry. The example fixture uses readable IDs; UUIDs can be used later without changing semantics.

Faults, model boundary, and observability

Source ingestion and notification delivery are separate simulator operations. A lost notification can leave the source version visible in the database while a strategy misses an early review. The dispatch guard still reads the database. A source change never observed by the system is a different failure and must be labeled separately. Replay records dropped notifications; restoring delivery is an explicit scheduled action, not an invisible repair.

A dedicated runtime projection must strip partition, family, template/group lineage, expected labels, fault assignments, evaluator notes, future events, and descriptive fixture IDs or filenames. Replace internal record IDs with stable opaque IDs within each episode and preserve a private evaluator mapping so citations can be scored. Apply the same observable projection to every baseline; human-readable development/example labels must never become benchmark hints. Test both initial input and every tool response/export visible to the system.

An optional model receives only allowed text and tool results. It returns amendment fields and candidate dependencies under a strict schema. It receives no dispatch tool, truth labels, future events, or benchmark family labels. Validate output before creating a proposal; refuse unknown entity IDs and enforce call/step limits. Log model identifier, prompt-template digest, token usage, errors, and price-date assumptions. Publish only reviewed synthetic traces.

For the proposed agent-input evaluation, generate and cache one sanitized proposal/dependency bundle for each of 40 cases × three trials (120 samples). Store an immutable sample ID, sanitized input hash, model configuration, raw-output status, validated output, dependency candidates, token usage, and content digest. Replay the identical bundle across all four strategies (480 episodes), using the same opaque-ID mapping and event schedule within each matched set. Cache an invalid-output or provider-failure status as well; do not regenerate until a favorable proposal appears. No additional model call occurs during these replays. This measures revalidation conditional on generated proposals, not an independently adaptive end-to-end agent comparison.

04 — Evaluation protocol

Status: proposed protocol, not preregistered, frozen, or executed. These are planning sample sizes, not a statistical power guarantee. A freeze record will replace open configuration choices after development. Build plan WP-09–12 defines the execution gates.

Question and estimands

Can selective revalidation after source-data changes reduce missed affected decisions and review work compared with cached approval, fixed expiry, and full revalidation? The primary comparison is revalidation selection and timing under a common dispatch guard. It is not a test of selective-only execution protection.

Prespecify two primary contrasts: selective minus fixed-expiry for missed-affected proportion; selective minus full for policy-evaluation work. Report both error and work dimensions. A lower work count accompanied by more missed decisions is a tradeoff, not unqualified improvement. All other contrasts are secondary and are labeled exploratory unless frozen otherwise.

Dataset, independence, and sealing

Create original synthetic scenarios with explicit rules and independently derived expected outcomes. Five families:

  1. Supplier status or eligibility changes.
  2. Price and quantity corrections.
  3. Contract or policy changes.
  4. Approval expiry, revocation, or authority changes.
  5. Delayed, backdated, or corrected records.

Each scenario includes pending amendments, at least one open committed order, and unrelated decisions. Proposed standard population: three decisions, as in the worked example. If a family needs more, freeze and report the population rule before generating test cases. A “material” case has at least one oracle-required action; a control has none under its declared horizon. Include benign value changes as well as unchanged controls.

Partition Per family Total Use
Development 5 material + 5 control 50 Tune rules, expiry, prompts, graders, and reporting.
Held-out test 20 material + 20 control 200 Final comparison only after freeze.
Agent subset of test 4 material + 4 control 40 Paired generated-input revalidation study.

The agent subset is part of the 200, not 40 additional independent cases. Select it by a frozen seeded procedure before inspecting outcomes. Group by the underlying incident or instantiated template; all variants stay in one partition. Generic family names can recur across partitions, but merely changing names/amounts does not make near-identical incident templates independent. Store template_group_id plus the highest shared incident/template-lineage identifier needed to join closely related derived templates; use that highest shared lineage for both partitioning and uncertainty clusters. Audit overlap and disclose how templates differ. Broad family labels alone do not establish common incident lineage.

Seal the test manifest, fixture files, oracle, and configuration with content hashes. During tuning, developers access development cases only; use a separate evaluator/reviewer for the test material where feasible. A solo developer cannot claim an independently protected test set if they inspect its answers. Record that limitation honestly and obtain an external reproduction set later. Public release of test data ends its usefulness as a secret future test set.

Four strategy definitions

Strategy Trigger and population Shared behavior
cached No source-event-triggered revalidation; explicit dispatch still checks current state. Same evaluator, knowledge access, escalation rules, and final guard.
expiry At a frozen interval, revalidate every pending and open committed decision due for freshness review. A completed order carries a monitoring timestamp even though approval expiry no longer authorizes an action. Same population eligibility and available response as other strategies.
full After each delivered source change, revalidate every pending and open committed decision. Does not gain hidden facts or a better guard.
selective After each delivered source change, select decisions from recorded dependency edges and evaluate those decisions. Same policy evaluator and dispatch guard; missing edges remain a failure mode.

Use exactly the same source materialization, notification schedule, review-service delay, approval semantics, and dispatch attempts per paired run. Freeze expiry and event-coalescing settings on development data. Full revalidation can examine unaffected decisions without necessarily escalating them: work and unnecessary escalation are separate metrics. All strategies may open investigations for committed decisions once selected and found affected. Do not withhold that response from a baseline.

Two modes and exact run counts

Control mode: fixed proposed amendments, no model calls. Initial reference dependencies are supplied from the scenario’s intended relationships. The clean condition therefore measures an oracle-dependency control system. When a schedule explicitly removes an edge, label it a corrupted-dependency stress condition; do not report it as perfect-oracle performance. Truth labels still remain outside the system.

Paired agent-input mode: after freezing model/version, prompt, decoding, tools, limits, and validation rules, generate one amendment/dependency bundle for each of 40 cases × three trials: 120 proposal-generation samples. Each sample receives only sanitized synthetic text and allowed tool evidence, with no strategy label or oracle information. Cache the actual output, validation status, captured dependencies, sanitized input digest, model configuration, token usage, and immutable proposal ID. Replay that identical cached sample across all four strategies, producing 480 episodes. Do not replace extraction errors with oracle values. An invalid output, refusal, or failed generation remains a recorded sample and produces the same no-proposal/failure input for all four strategies; do not resample until success. Report extraction/dependency errors at the 120-sample level and downstream outcomes at the 480-episode level.

This paired-input design isolates revalidation behavior conditional on proposal generation. It includes observed proposal errors but does not compare four independently adaptive end-to-end agents. Any independent end-to-end sampling, adaptive model calls during replay, or second-model replication requires a separate frozen protocol and additional budget. Sharing trial labels alone would not pair stochastic proposals; the cached content and evidence digests must match.

Mode Calculation Runs
Deterministic control 200 scenarios × 4 strategies × 3 schedules 2,400 episodes
Agent proposal generation 40 scenarios × 3 sampled proposals 120 generation samples
Paired agent-input replay 120 cached samples × 4 strategies × 1 assigned schedule 480 episodes

For the agent study, assign one of the three schedules to each scenario before running it, balancing schedule allocation within family/material strata as closely as 40 cases permit. Store the assignment in the subset manifest. Do not run all three schedules and still call the total 480; that would produce 1,440 episodes. Three generation trials measure proposal variability, not three independent underlying cases. Preserve each sampled proposal and replay it unchanged across strategies; hosted generation itself may not be exactly reproducible, but its recorded output is inspectable and replayable. The 120 generation samples are a separate accounting stage, not an additional 120 strategy episodes. Count all model/tool calls made within each bounded sample, including failures.

Three prescribed schedules

Proposed stress recipes below must be made executable and frozen on development cases. They are not a Cartesian sweep. For each family, document equivalent valid transformations and preserve material/control labels under the final oracle.

ID Recipe What it tests
S0 canonical Complete recorded dependencies; source observations and notifications delivered in timestamp order; ordinary dispatch. Reference behavior; supplied dependencies are explicitly an oracle condition in control mode.
S1 delayed Deliver a nonmaterial older notification after a newer notification; delay a designated observation; remove one designated recorded dependency edge after initial capture. Time/knowledge handling and dependency loss. The same edge corruption and event inputs reach every strategy.
S2 boundary Materialize a designated source update but suppress its notification through the observation horizon; interleave another designated update after preflight and before final transaction acquisition. Missing event notification and stale preflight. Separate unit tests cover a writer blocked during the transaction.

For a control case, the injected update remains benign; dependency removal alone must not manufacture a business-invalid label. Do not inject a future source update invisibly and then claim a system failed to use knowledge it never received. Report cases whose invalidity is knowable by the current observation cutoff separately from retrospective invalidity revealed later.

Fix virtual-time horizon, designated edges/events, delays, review-service times, dispatch attempt times, expiry, and seeds in the freeze file. A proposed development starting point is a 30-minute horizon with an expiry interval chosen from 5, 10, and 15 minutes on development data. These values are tuning candidates, not frozen parameters. Count extra exploratory sweeps, guard-off ablations, or new stress recipes separately.

Oracle and scoring

An evaluator-only truth file describes, for each decision/change pair, whether review is required, the correct pending/committed consequence, earliest knowable time, and the eligible observation window. It is never passed into a strategy or agent. The runtime projection also removes split/family/template metadata, injected-fault labels, descriptive scenario IDs and file paths. Use opaque per-episode record IDs with an evaluator-only mapping, preserving the same substantive evidence for every strategy. Audit tool responses as well as the initial prompt; a label-free prompt with a revealing filename is still leakage. Use executable state assertions for action outcomes; use a human reviewer to audit realism and ambiguous policies. A model-based judge is unnecessary for the core deterministic truth.

Measure Definition and denominator
Missed affected decisions Oracle-required decision/change pairs with no correct hold or case by the frozen deadline / all oracle-required pairs. Report pending and committed separately.
Unnecessary escalations Oracle-unaffected decision/change opportunities receiving a hold or investigation / all oracle-unaffected opportunities. Also show absolute queue size.
Invalid pending allowed Invalid dispatch attempts that commit / oracle-invalid dispatch attempts, using currently knowable facts; show retrospective invalidity separately.
Completed routed correctly Affected open committed decision/change pairs with the required case / affected open committed pairs. Never count an automatic reversal as correct.
Valid-action completion Oracle-valid eligible actions committed by horizon / oracle-valid eligible actions. Include holds and timeouts in the denominator.
Detection delay First correct action time minus earliest knowable time; show distribution for detected cases plus missed fraction and censoring horizon.
Revalidation work Policy evaluator invocations, decisions selected, records read, and queue entries; report per scenario and per affected pair.
Cost/runtime Model tokens/calls and measured provider cost assumptions, local runtime/hardware, and human review effort only if actually measured.
Agent errors Field/dependency precision and recall against intended references; invalid schema, unknown IDs, missing evidence, and refusal rates.

When a denominator is zero, print “not applicable (0 eligible)” rather than 0% success. Count a crash as an error, not a valid abstention. Preserve a run-status table and sensitivity analysis for incomplete runs; never calculate success only over convenient survivors. Report material/control strata and each family before an aggregate.

Uncertainty and decision rules

Compute paired differences for each scenario under matched schedules and trials. Average repeats within scenario for a scenario-level estimate; resample at the highest shared incident/template-lineage level when scenarios or derived templates share one. Keep the four strategy outputs for each cached proposal together, and do not treat its three generation samples as independent scenarios. Preserve all strategy outputs for a sampled group together. Proposed method: 10,000 seeded cluster-bootstrap replicates with 95% percentile intervals, accompanied by raw paired counts and the number of independent groups. Few groups or near-zero events make intervals fragile; disclose this rather than implying precision from 2,880 repeated runs.

Predeclare that an efficiency claim requires lower work with an acceptable error/completion tradeoff whose margin is chosen on development data and justified by the synthetic task. Do not choose the margin after seeing test results. A safety-unit-test gate can require zero known-invalid executions in specified races; finite benchmark zero errors does not establish zero real-world risk.

Record dataset/protocol/code digests, source-event ordering, run seed, policy version, model ID, prompts/tools, grader version, price date, machine details, and all deviations. If a grader defect is discovered, explain it, version the correction, and rescore every affected strategy consistently. Freeze changes to the system require a new evaluation version. Publish negative results and missing-data limits. No synthetic result supports financial-loss, compliance, or productivity claims by itself.
